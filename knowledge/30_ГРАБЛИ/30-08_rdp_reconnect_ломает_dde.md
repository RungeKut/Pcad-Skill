# Переподключение RDP убивает DDE-канал

## Что происходит

После переподключения RDP (сессия пересоздаётся: rdp-tcp#19 → #21, ID
 тот же) `pk.dump` любой схемы даёт `TOpenDesign: [32001]
DBX_CONNECTION_ERROR` — и на своём Sch.exe, и при host open к уже
запущенному и загрузившему файл редактору. Файлы в порядке: на скрытом
рабочем столе тот же Sch.exe тот же файл открывает и выгружает.

## Почему

DDEML-состояние (брокер DDEMLMom, регистрации сервисов) привязано к
window station сессии; при пересоздании сессии старые регистрации
теряются/протухают, а соединения в унаследованной от старой сессии
среде не проходят. Подтверждения уровня API нет — вывод по симптомам.

## Как правильно

Вынести пару целиком в свежую window station — скрытый рабочий стол
(HiddenDesktop-Skill): запустить там Sch.exe с копией дизайна, затем там
же cmd, который подаёт JSON-команды в DbxHost.exe и собирает stdout:

```
d.launch([Sch.exe, копия.sch]); sleep
d.launch(["cmd","/c","DbxHost.exe < cmds.txt > out.txt"])
```

в cmds.txt: open(wait_sec) → components/nets → shutdown. Результат —
JSON-строки в out.txt. Тот же приём — для живого режима, когда Sch.exe
человека запущен в новой сессии: запускать host тоже в её window
station нельзя из унаследованного процесса.

## Как неправильно

* Диагностировать 32001 как «битый файл» или «чужой экземпляр» (30-03):
  контрольный тест на заведомо читанном файле отделяет этот случай.
* Перезапускать Sch.exe — не помогает: проблема не в процессе редактора.

## Чем подтверждено

2026-10-31: сессия сменилась, 4 запуска pk.dump (два разных файла,
локальная копия и сеть) — все 32001; host open к живому Sch.exe — 32001;
пара на HiddenDesktop — open ok, 74 компонента выгружены.
